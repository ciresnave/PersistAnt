kind: a PostgreSQL `void` result reads as `()`: `FromValue for ()`, `FieldKind::Unit`, the driver carries `void` as NULL (issue #229)
---
`SELECT void_fn($1)` through `sqlx_query!` (Humboldt gap 3, issue #229) did not compile: sqlx describes a `void` column as `()` and `()` had no `FromValue` (`the trait bound (): FromValue is not satisfied`). Now `persistant_relational::FromValue` is implemented for `()` (it accepts only NULL; `FieldKind::Unit` is new and the enum is `#[non_exhaustive]`), and `PgBackend`'s decoder carries a `void` column, a zero-length datum that is not NULL on the wire, as `Value::Null` instead of refusing the type (`docs/DECODER-AUDIT.md` has the row). Because sqlx cannot say a void column is non-null, `sqlx_query!` types it `Option<()>`, which reads `None`; `Row::get::<()>` reads `()`. MySQL, MariaDB and SQLite have no void type and are unchanged.

Reproduced red first against a real PostgreSQL 16: a hand-written offline `.sqlx` entry for `SELECT persistant_void_fn($1)` (the shape Humboldt hit; the function inserts a row) failed to compile with exactly the reported error. Now the statement compiles, runs, and its side effect is there; the driver test reads `pg_sleep(0)` as `()` and `None`, and a non-NULL value is not a void. Removing the decoder arm fails the driver test.
