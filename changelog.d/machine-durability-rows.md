`SqliteBackend::open_secure_wal` (ROADMAP row 38, opt-in; the default profiles are unchanged): WAL with `secure_delete` on and a truncating checkpoint after every write, so a plain delete leaves no bytes in the `-wal` file. Tested by raw-file read-back with the default WAL profile as the control (it keeps the canary) and a mutation that skips the checkpoint (the canary stays in the `-wal`). Cost measured once on a loaded box, interleaved: a median 0.31 of plain WAL's write rate (`bench/secure-wal-cost.txt`, `examples/secure_wal_cost.rs`). A reader holding the log defers the truncation to the next write; not registered as a profile id.

ROADMAP row 30, second half: `examples/pg_vs_auth_sql.rs` and `bench/pg-vs-auth-sql.txt` (in the next PR) (design note `bench/pg-vs-auth-sql-design.md`, committed first). The key-value layer against auth-framework's own PostgreSQL SQL, interleaved pairs on a loaded box (n=30): about 2.0x on a token check and about 2.9x on a token store (more statements, not slower statements); session read and kv get not separable from parity. Example and bench note only, no library change.

ROADMAP row 47 (row 30 follow-up): concurrency and its cause. `bench/pg-vs-auth-sql-concurrent.txt` (in the next PR): a token store costs about 10x the direct upsert at 8 workers, reads unchanged. `bench/pg-store-lock-variant.txt` (in the next PR) (with `bench/no-batch-lock.patch`, a measurement patch not in the tree): skipping only the global `persistant_kv_batch` lock row takes that from 12.5x to 2.9x, so the one lock row is the cause. The fix (striped per-key locks, design in `bench/pg-store-lock-design.md`) is built: on PostgreSQL `KvOnRelational::batch` now locks one stripe row per key (256 stripes, ascending order) in place of the one global `persistant_kv_batch` row, so batches on different keys run together; a token store at 8 workers falls from about 12x to 3.9x the direct upsert (`bench/pg-store-lock-stripes.txt` (in the next PR); the predicted 2.7 to 3.0 was not met). Tests in `kv_batch_stripes.rs` (red first, two mutations caught): same-key and overlapping-key workers lose no update and take no deadlock retry, a refused or cut-off batch leaves no partial rows. New: `batch_stripe`, `BATCH_STRIPES`, `KvOnRelational::batch_retries`; `open` adds stripe rows 2..=256 to `persistant_kv_batch` on PostgreSQL (existing rows kept). MySQL and MariaDB batches are unchanged (still one row). NOT Breaking: no signature, error or isolation guarantee changes (each batch is still one READ COMMITTED transaction, batches sharing a key still serialise); batches on disjoint keys no longer exclude each other, which was never promised.
