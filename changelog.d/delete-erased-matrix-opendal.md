`persistant_opendal::certify_delete_erased` records `blob.delete_erased` for `opendal-fs` (with and without `atomic_write_dir`: **on**, both controls held) and for `opendal-memory` (**off, missing**: no file to overwrite). The `opendal_matrix` example adds `kv.delete_erased` rows for `KvOnBlob` over the same configurations: on for `fs` in-place and `fs` with a scratch directory; off as missing for the memory service and for strict `fs` without a scratch directory (no `kv.put` there). Both ids are in the vocabulary with their contract. The reading is a second hard link to the file made before the delete: a plain delete leaves the canary readable through it (known-bad control), `delete_erased` does not; with the overwrite removed the certify test fails. `matrix/opendal.tsv` gains the 7 rows.
