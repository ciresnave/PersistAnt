kind: Added: `Lease::token()`, a fencing token strictly greater for each later holder of a key (leaf `lock.fencing`), and `Lease::holder`
---
**Compatibility note (not an API break; additive API):** the stored lease value changes from `owner` to `owner`, `\0#`, token. A mixed-version fleet fails safe, not silently: a pre-fencing holder or contender that meets a value with a token is refused by every call (its `put_if_absent` finds the key taken, its `compare_and_swap` renew and `compare_and_delete` release expect the bare owner and return `false`), so it neither takes the key over nor renews or releases it, and the new holder is untouched. A pre-fencing holder renewing means "I must stop acting as the holder", so an old holder that meets a new value stops. The reverse also fails safe: this version reads an old value as token 0 and takes the key over only after it expires. Upgrade every holder of a key together; code that reads the raw key and compares it to the owner name will see the suffix (use `Lease::holder`). Verified by emulating the old calls against a new value (`mixed_version_tests`), not by running an old binary: UNVERIFIED against a real old build.

`Lease::acquire` now takes a number from a never-expiring counter key (`<key>#fence`, bumped with `cas::update`) after it wins the lease, and writes it into the lease value; `Lease::token()` returns it. A later holder of the same key always gets a larger token, including after expiry and after a lost race (a loser takes no number); renew keeps the token. A resource that remembers the highest token it has seen and refuses a lower one is protected from a stale holder; the docs say the token protects nothing that does not check it, that its order does not depend on any clock, and that the clock (the database's on SQL, the host's on SQLite) only decides when a lease may be reclaimed. `Lease::holder(kv, key)` reads the owner and token; a value written before fencing reads as token 0.

`acquire` also confirms its win with a compare-and-swap, so `PutIfAbsentNotExclusive` no longer turns the lease leaves off (it still turns `kv.put_if_absent` off). New matrix leaf `lock.fencing` (24th kv/lock leaf), off with a typed refusal on a blob store, on for SQLite, PostgreSQL, MySQL and MariaDB. Verified: strictly increasing tokens across sequential, expired and 16-way racing holders; `CasIgnoresExpected` turns the leaf off; a counter that does not increment makes it fail ("a later holder got token 1 after 1"), reverted. The registry docs said `lock.*` is not offered; it is listed and gated like `kv.*` (read back with `tests/registry_lease.rs`), and the docs now say so. ROADMAP row 41 step 2.
