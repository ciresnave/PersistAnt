kind: `BatchOp::DeleteErased`: an erased delete inside an atomic batch (SQLite); `RelationalTx::erase_on_commit`
---
New `BatchOp::DeleteErased { key }` (`BatchOp::delete_erased(key)`): as `BatchOp::Delete`, and where the backend can, the stored bytes are overwritten as part of the same atomic unit. SageAnt needs this for forgetting a whole lineage (documents, links, index postings) in one batch (relayed by the PM). On SQLite (`sqlite`, `sqlite-full` including its WAL, `sqlite-secure`) the batch is **one transaction** with `secure_delete` on, and the write-ahead log is truncated after the commit; on memory, and on any backend whose transaction cannot erase (PostgreSQL, MySQL, MariaDB; a blob store has no batch), the **whole batch is refused with `Unsupported` before anything runs**, never quietly done as a plain delete. New default method `RelationalTx::erase_on_commit` (default `Unsupported`; SQLite implements it; `Faulty`, `Traced`, `Bounded` and the registry's `AnyTx` forward it), used by `KvOnRelational::batch`.

Honest limit, tested: the log truncation is a step after the commit. If a reader holds a snapshot and the log cannot be truncated, the batch has committed (the keys are gone) and the call returns an error saying the write-ahead log could not be truncated, rather than `Ok`; calling it again is harmless. The truncating checkpoint now waits at most about a second for readers (it used the connection's 30-second busy timeout, five times over, in the first version of this change); `execute_erased` shares the helper and now reports the same condition instead of ignoring the checkpoint's busy flag.

Verified through the registry (async and blocking, bounded and not) with raw-file read-back: a plain batch delete leaves the canary in the files (control), the erased batch leaves none on `sqlite` and `sqlite-full`; a refused `Require` changes nothing; an erased delete mixes with puts and plain deletes in one batch; memory refuses the whole batch and applies nothing; a held reader makes the batch report the untruncated log (and the same batch without the reader completes). Three mutations each fail tests: no `secure_delete`, no truncation after commit, `KvOnRelational` not requesting the erasing transaction.
