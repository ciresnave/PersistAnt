---
The leaf that lets the gate see whether a store can forget a document's terms, and a correction to what the SQLite rows claim. **sageant measured (2026-11-15) that an erased delete on `sqlite` and `sqlite-full` leaves stale in-page fragments** of earlier writes (page splits and rebalancing while `secure_delete` was off): after forgetting 30 records of about 700 bytes some of the text stays in the files, while `sqlite-secure` keeps none. The earlier `kv.delete_erased` rows passed because they forgot one key. Both trials now forget thirty (a plain removal on a default-profile database is the control), so the rows read: `kv.delete_erased` and `text.index.erased` **off, wrong** on `sqlite` and `sqlite-full`, **on** on the secure profile (config `secure_delete=on`, which the `sqlite-secure` registry id reads); **off, missing** for PostgreSQL, MySQL, MariaDB (`erase_on_commit` is unsupported) and the four `KvOnBlob` configurations on OpenDAL (no atomic batch). A registry need for either leaf is now met by `sqlite-secure` only. The limit is stated in the README, the design note, the `delete_erased` and `remove_many_erased` docs and the `sqlite` and `sqlite-full` notes. New test `tests/text_erased_many.rs`: the plain removal finds the terms (control), `sqlite-secure` leaves none for the text index and for kv values, and `sqlite` and `sqlite-full` keep some (so a future fix shows as a failing test to update). `text.index.erased` is in the vocabulary; the `checked_in_matrix_*` counts move (+1 per server file, +4 for SQLite) and the server tests expect the leaf off as missing. The PostgreSQL, MySQL and MariaDB rows are written by hand to the generator's format and checked by the CI matrix diff against the real servers.
