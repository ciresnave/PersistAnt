kind: matrix leaf `text.index.erased` and its rows (row 39, step 5)
---
The leaf that lets the gate see whether a store can forget a document's terms: **on** for `sqlite` and `sqlite-full` (including its WAL), **off, missing** for PostgreSQL, MySQL and MariaDB (`erase_on_commit` is unsupported there, so `remove_many_erased` refuses before changing anything) and for the four `KvOnBlob` configurations on OpenDAL (no atomic batch). The SQLite rows are read back from the files: twenty filler documents and a document that carries a canary term are indexed, a plain `remove_many` is the known-bad control (the term stays in the files on both profiles), and `remove_many_erased` leaves it in none; the generator also checks the document is gone and one document was removed. The server and blob rows come from the call itself through the new `text_conformance::erased_unsupported(kv, base)`, which leaves nothing behind. `text.index.erased` is in the vocabulary; the `checked_in_matrix_*` counts move (+1 per server file, +2 for SQLite) and the server tests expect the leaf off as missing. The PostgreSQL, MySQL and MariaDB rows are written by hand to the generator's format and checked by the CI matrix diff against the real servers.
