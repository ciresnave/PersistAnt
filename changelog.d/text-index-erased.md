`persistant_kv::text::TextIndex::remove_many_erased(index, doc_ids)` (feature `text-index`): as `remove_many`, with the postings (their keys hold the documents' terms) and the document records removed by `BatchOp::DeleteErased` in the **same atomic batch**, so on SQLite (`sqlite`, `sqlite-full` including its WAL, `sqlite-secure`) the terms are overwritten in the file and the write-ahead log is truncated after the commit; a backend that cannot erase inside a batch (memory, PostgreSQL, MySQL, MariaDB) returns `Unsupported` before anything changes. This is the whole-document forget SageAnt asked for; it is simpler than the tombstone-and-journal sequence the design note first drew, because the erased batch is atomic (the design note says so). If a reader keeps the log from being truncated the call returns an error after its batch has committed (the documents are gone, their terms may still be in the log); **calling it again with the same ids finishes the job**: documents already removed are ignored and a repeat still runs an erased step (a batch with an erased delete of a key that is not there), which truncates the log. Not covered, stated: a posting or record an earlier plain `put` replaced or a plain removal deleted, unless the store is `sqlite-secure`; copies a file system, snapshot or backup keeps.

Verified through the registry with raw-file read-back of a canary term on `sqlite` and `sqlite-full`: a plain `remove_many` leaves the term in the files (control), `remove_many_erased` leaves none, the rest of the index and the totals are right, an unknown id is ignored; memory refuses and changes nothing; with a reader holding the log the call reports it, and the repeat call leaves the term in none of the files. Two mutations each fail tests: treating the erased removal as plain, and dropping the repeat step. Not yet: the matrix leaf `text.index.erased` and its rows.
