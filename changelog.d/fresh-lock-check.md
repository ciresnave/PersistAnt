kind: Published versions resolve to a recorded OpenDAL; the OpenDAL key is the version that ran
---
Checked on 2026-11-22 against the crates.io tarballs: a fresh `cargo update` of a project depending on `persistant =0.18.28` and on `=0.18.30` (feature `registry`) resolves `opendal 0.59.5`, which `matrix/opendal.tsv` records, so both open without a refusal. `0.18.27` was never published (crates.io lists 0.18.30, 0.18.28, 0.18.23, ...), so there is nothing to check for it. The OpenDAL matrix key is the runtime `opendal::raw::VERSION` (the library that ran, `0.59.5`), not the `0.59.4` floor in `Cargo.toml`: the rows record the behaviour of the library that was exercised. `opendal_rows_are_keyed_by_the_version_that_ran` pins this with a known-bad control. No code change.

Also: `Cargo.lock` moves `url` 2.5.8 to 2.5.9 and `form_urlencoded` 1.2.2 to 1.2.3 (RUSTSEC-2026-0592, a stack overflow in `Url::origin()` on nested `blob:` URLs, reached through `opendal-core`; `cargo deny check advisories` failed on it). `deny.toml` drops the RUSTSEC-2026-0459 ignore (it no longer matches: the lock holds sqlx 0.9.1) and renews the RUSTSEC-2026-0543 (chrono) ignore with its reason, keeping the expiry 2026-12-17: moving `persistant-relational` off chrono alone does not clear it, because `persistant-sqlx` enables sqlx's `chrono` feature for chrono consumers.

Also: `blob.durable` gets its power-loss harness (ROADMAP row 4): the guest example `machine_vm_blob` and `run.ps1 -BlobBinary` cut power on a Hyper-V guest while files are being written through `std-synced` (must hold), `std-unsynced` (the known-bad control, must lose) and OpenDAL `fs` with and without `atomic_write_dir` (measured: held or lost is the finding). No matrix row and no capability changes until a run shows it; `blob.durable` stays off. Row 42 (chrono) closes as "stays ignored" with Humboldt's estimate recorded.

Also: a consumer-CI check (ROADMAP row 18): `cargo run -p persistant-sqlx --example consumer_ci` runs the key-value suite against the caller's own PostgreSQL (or SQLite) and exits non-zero when a leaf named in `PERSISTANT_NEEDS` is not there or is not a known leaf; recipe and a GitHub Actions job in `docs/CONSUMER-CI.md`. Tested on SQLite: pass (exit 0), a typo (exit 2), a leaf that is off (`kv.bounded_call`, reported MISSING). Not run against PostgreSQL here.

Also: ROADMAP row 13 answered in `docs/DESIGN-KINDS.md` §10: neither SQLite nor MySQL publishes a per-feature-code conformance list (surveyed from their documentation on 2026-11-22; PostgreSQL's states "at least 170 of 177" Core features). Their `rel.*` rows keep coming from tests.

Also: `docs/DESIGN-NONSQL-HELPERS.md` (ROADMAP row 19, design only): on blob stores `lock.lease`, `lock.fencing` and `kv.purge_expired` stay refused (no compare-and-delete, so a takeover or a purge can remove a fresh value); proposes a prefix sweep for keys that carry their time and a migration ledger of exclusive creates. No code or behaviour change.

Also: `persistant_blob::retention::purge_prefix_older_than` (ROADMAP row 19, slice 1): deletes the keys under a prefix whose period, read from the key by a caller-supplied parse, is strictly before a cutoff; unparsed keys and other prefixes are kept. Correct only when a key names its period and is never written again after it; the module says so first. Added API, no change to existing behaviour. Tests: the key at the cutoff survives (known-bad control: `<=` fails it, run), unparsed and foreign keys survive, more than one list page.

Also: `persistant_blob::ledger::Ledger` (ROADMAP row 19, slice 2): a migration ledger for non-SQL stores. Per step an exclusive `<id>.claim` and a `<id>.done` marker; four racing migrators run a step once; a failed step releases its claim; a claim with no done marker (a migrator that died) is reported by who and when, never taken over, because a blob store has no compare-and-delete. Added API. Tests include a known-bad control (the same race without the claim runs the step more than once) and a mutation (claim skipped: the race test and the held-claim test fail, run). The dead-migrator state is made directly in the test; a killed-process test is not built.
