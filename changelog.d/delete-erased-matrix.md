`persistant_opendal::certify_delete_erased` records `blob.delete_erased` for `opendal-fs` (with and without `atomic_write_dir`: **on**, both controls held) and for `opendal-memory` (**off, missing**: no file to overwrite). The `opendal_matrix` example adds `kv.delete_erased` rows for `KvOnBlob` over the same configurations: on for `fs` in-place and `fs` with a scratch directory; off as missing for the memory service and for strict `fs` without a scratch directory (no `kv.put` there). Both ids are in the vocabulary with their contract. The reading is a second hard link to the file made before the delete: a plain delete leaves the canary readable through it (known-bad control), `delete_erased` does not; with the overwrite removed the certify test fails. `matrix/opendal.tsv` gains the 7 rows. `matrix/sqlx-sqlite.tsv` records `kv.delete_erased` **on** for `sqlite` and `sqlite-full` (the database file, `-wal` and `-journal` read back for a canary; a plain delete on another database is the known-bad control), and `matrix/sqlx-{postgres,mysql,mariadb}.tsv` record it **off, missing**, from the call (`KvOnRelational` returns `Unsupported`: those servers keep a deleted tuple until vacuum / purge, and the log and backups keep it). The shared `ErasedTrial` / `erased_row` live in `persistant_core::erased`; the PostgreSQL, MySQL and MariaDB rows were written by hand from that known result and are checked by the CI matrix diff.
