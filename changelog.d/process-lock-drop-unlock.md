kind: **Fix**: a dropped `ProcessLock` is released even while a forked child holds a copy of the file
---
- **Fix (`persistant-opendal`, issue #220): `ProcessLock` unlocks explicitly on drop.** A `flock` belongs to the open file *description*, not the descriptor, so a child forked while the lock was held kept it held after the owner dropped it, until the child `exec`ed (close-on-exec, which `std` already sets, only acts at the `exec`). It showed as a flaky `process_lock.rs` test in CI (PR #219, run 43196444637, "a dropped lock was not released"). `Drop` now calls `File::unlock`, which acts on the description whoever else holds a descriptor to it. Born-red, then green on Linux (rust 1.98): a unit test where a duplicated descriptor stands in for the child's copy (failed deterministically before), and a stress test that spawns children from four threads while the lock is taken and dropped 4000 times (failed within 0.01 s before; green 5 runs of 5 after). A close-on-exec test (`/proc/self/fdinfo`) pins the part `O_CLOEXEC` does cover. Windows: `std` handles are not inheritable and the tests there pass; the new tests are Unix-only. No API change.
