kind: fix: `open_named("sqlite-full", ..)` with a `rel.*` need answered `Unmet` / `NoRow`
---
**Defect in 0.18.12 (and earlier, since `sqlite-full` gained relational rows in 0.12.1): a patch release is warranted.** `registry::open_named` checks the gate twice, the second time against the backend it actually opened. For the relational surface it set the `dialect` fact from the backend's *name*, which is `sqlite-full` for the durable profile, while every recorded row says `dialect=sqlite`; so the second lookup found no row and `open_named("sqlite-full", .., rel.values)` (and every other `rel.*` need) was refused, although `providers` listed `sqlite-full` for the same need. `sqlite` worked only because its name equals its dialect, and the kv path is unaffected. The fact now comes from `RelationalBackend::dialect()`, which is `sqlite` for both profiles (and `postgres`, `mysql`, `mariadb` as before).

Found while testing `delete_erased` through the registry (the relational handle of `sqlite-full` could not be opened to test it). New tests, red before the fix (28 listings failed on the unfixed tree, all `sqlite-full` with a `rel.*` need): `tests/registry_listed_opens.rs` runs, for every id the local build offers and every capability in the vocabulary, alone and beside `kv.get`, `providers` then `open_named` and fails if a listed id is refused at open (the generic form of this defect), plus an end-to-end open of `sqlite-full` for `rel.values` and `rel.transaction` that runs a statement; `tests/registry_servers.rs` runs the same check on each server the CI jobs provide (the server ids are not opened locally: a port nothing listens on costs a connection timeout per listing).
