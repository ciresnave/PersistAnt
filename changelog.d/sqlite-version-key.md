kind: HOTFIX: `open_named` on a SQLite newer than the recorded rows
---
**0.18.28, 0.18.23 and 0.17.12 (the lines checked) are refused on a fresh lockfile.** The second gate in `open_named` matches rows on the version the opened backend reports at run time (`SELECT sqlite_version()`); a fresh lock resolves libsqlite3-sys 0.40.0 (SQLite 3.54.1) and the rows said 3.51.3, so every need was `unverified(no row)`. Reproduced on Windows x86_64 (not OS-specific): the same call opens with the committed lock and fails after `cargo update`. CI never saw it because every job is `--locked`. **Workaround for a consumer on an affected release: pin `libsqlite3-sys = "=0.37.0"` in its lockfile** (`cargo update -p libsqlite3-sys --precise 0.37.0`).

Fixed here: rows are recorded for SQLite 3.54.1 on linux, windows and macos (the 3.51.3 rows stay, for lockfiles that still resolve it); the open error now names what was opened and the nearest recorded version (`sqlite (opened kv-on-relational:sqlite 0.18+3.54.1; no row for 0.18+3.54.1; nearest recorded 0.18+3.51.3)`), tested red-first through an injected version; a scheduled job (not a required check) re-resolves the lock, runs the generators on three OS and fails loudly when no row exists for the newest bundled SQLite, so rows follow the lock. A SQLite or opendal or server version nobody recorded is still refused, by design: a `yes` for a version nobody ran is an unearned claim. The opendal rows are keyed by the version that ran (`opendal::raw::VERSION`, the resolved one), not the `Cargo.toml` floor; a test says so.
