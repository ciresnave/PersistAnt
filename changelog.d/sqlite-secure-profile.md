kind: opt-in SQLite `secure_delete` profile, registry id `sqlite-secure`, capability `storage.secure_delete` (row 38 follow-up)
---
`SqliteBackend::open_secure(path)` opens with `secure_delete` on for every connection of the pool and the rollback journal named explicitly: content a statement frees or overwrites is zeroed in the database file as it goes, which closes the case `execute_erased` cannot reach afterwards (a value an earlier plain `put` overwrote or a plain `delete` removed). It reports as `sqlite`; `secure_delete()` says it was asked for. The registry offers it as the new id `sqlite-secure` (`known_ids` grows by one), listed with the recorded row `storage.secure_delete` (config `dialect=sqlite;secure_delete=on`), so a consumer names it as a **preference** in its needs (`prefer(vec![storage.secure_delete])`): it orders `sqlite-secure` first and never excludes `sqlite` or the others.

Verified by scanning the raw files: two canary values, one overwritten by a short value and one deleted by plain statements, leave a canary in the file on the default profile (the known-bad control) and none on the secure profile; the registry test repeats it through the handle; with the pragma turned off the test fails. **Not WAL:** measured, `secure_delete` does not reach a WAL file's earlier page images (the canary stayed in the `-wal`), so there is no durable form and `sqlite-full` does not claim the row; on a WAL database use `kv.delete_erased`, which checkpoints. Not covered: the rollback journal's pre-images (removed, not zeroed, at transaction end), and anything a file system, snapshot or backup keeps.
