## Correction (2026-10-29, 0.12.3): SQL translation is NOT compile-time only
An earlier version of this record, `ROADMAP.md` and the addendum said that translation is compile-time with no run-time cache. **That is true of the `sql!` macro only and false of the crate.** `crates/persistant-kv/src/translate.rs` (`Translator::prepare`, called on every statement from `on_relational.rs`) calls `unisql::translate` **at run time** to turn the key-value adapter's PostgreSQL statements into SQLite, MySQL and MariaDB text, keeps the result in a `Mutex<HashMap<String, (String, Vec<u32>)>>` keyed on the raw SQL string (filled on first use, never pre-populated), and reorders bound parameters by `param_order` for the positional dialects. Found by the PM's claim read of origin/main 60dfde6; the earlier claim was replaced everywhere it appeared (this file's first-pass table row for idea 11, the conditions paragraph and the needs-review paragraph; `ROADMAP.md` patent-conditions table).
**Conditions that hold today:** (a) the statements translated at run time are **constants written in this crate, never a caller's own SQL**; (b) **no provider declares `rel.source_dialect`** (the capability id exists in `persistant-core` and `docs/DESIGN-KINDS.md`, but nothing in code offers translation of a caller's statements), so a caller cannot hand PersistAnt a foreign-dialect query. Both are standing conditions: do not add a provider for `rel.source_dialect`, and do not route a caller's SQL through `Translator`, without re-reading US20140280259A1 and US9582500B2 and asking CireSnave (see verdicts below).

## Ideas swept
1. Capability-filtered backend selection: required capability ids plus an ordered preference list; backends meeting every requirement returned sorted by preference then measured speed with a reason per rank; an unmet need is an error naming each backend's unmet id (never a closest match); the chosen backend's stable id is stored in configuration and opened by id.
2. A backend capability is boolean, present only when an automated conformance test passes; results live in a committed matrix file CI regenerates, and CI fails if the committed file differs from what the code certifies.
3. Measured speed data per backend, configuration and workload, with host CPU load and free RAM at start and end, a concurrent multi-task harness, rows measured under high load flagged as not evidence; used to rank backends.
4. Key-value store on a blob store: atomic put by temp write and rename, ordered scan by listing, capabilities derived from the blob store's declared configuration facts.
5. Layered storage abstraction: trait crates for blob, key-value and relational, and generic adapters (key-value on relational, on blob).
6. Whole-OS durability check: write on a VM guest, acknowledge, cut the guest's power with no sync, boot, verify every acknowledged key; a known-bad control must lose writes in the same cycle or the test is invalid.
7. Process-kill durability test with a known-bad control that must fail.
8. Atomic replace: temp file in a separate scratch directory, fsync, rename over the target, with a recorded configuration fact feeding capability declaration.
9. Compile-time macro validating embedded SQL against a committed schema snapshot (names through aliases and joins, INSERT arity, omitted NOT NULL, ON CONFLICT unique key), erroring only when certain, unknown names pass.
10. Producing the snapshot from migration DDL without a database, from a live catalog, or by scratch apply; a check mode fails when the committed snapshot differs.
11. Compile-time translation of one statement into each enabled dialect (PostgreSQL, MySQL, MariaDB, SQLite), refusing by construct, with per-target parameter order (the `sql!` macro). **11b (added by the 2026-10-29 correction): run-time translation of the key-value adapter's own constant PostgreSQL statements for SQLite, MySQL and MariaDB, with a lazily filled cache keyed on the SQL text and parameter reordering.**
12. Compile-time check that bound argument types fit the column's type class and a row struct matches selected columns.
13. Verifying a migration set on a fresh scratch schema per engine against the committed snapshot.

### Ideas added (what the code does, with the version that added it)
14. **Evaluation by an external evaluator with three states (0.12.0).** Selection is decided by `capant::evaluate` over the matrix: each needed capability id is `yes`, `no` or *unverified*; a `yes` row with no probe id counts as unverified (`no evidence`), not on; the unmet report lists unmet and unverified ids separately, with the reason for each.
15. **Durability as an ordered capability (0.12.0).** `durability.process` and `durability.machine`: a provider that declares a class has a row for it and every lower class, its declared basis is the evidence; a need for more than the volatile class requires the id; the shortfall is reported, never rounded.
16. **Evidence tied to the software version (0.12.0).** Matrix rows carry the crate version's first two numbers; the registry refuses a provider whose rows are for another version, so evidence is earned again per version (CI regenerates them).
17. **Registry serving three storage kinds from one configuration id (0.11.13 to 0.11.17).** Providers are listed per kind (blob, key-value, relational) from capability rows; one handle exposes the surfaces of the kinds the needs named; the displayed durability is the weakest of those kinds; a kind a provider does not serve is "no row", never a closest match.
18. **Shared namespace between kinds (0.11.14).** Reserved key prefixes (`kv`, `kvx`) refused on the blob surface where the key-value store keeps its files, applied on every provider so behaviour does not depend on the id; a listing leaves them out.
19. **Blocking mirror over async handles (0.11.17).** One worker serves every kind; a transaction is run as a statement list in one call and rolled back if one fails; a transaction held open across blocking calls is not offered.
20. **Tracing decorator (0.11.4 to 0.11.6).** A wrapper over each storage trait (key-value, blob, relational) emitting spans with shared names across the three kinds.
21. **Fault-injection decorator (0.11.8, 0.11.10).** A wrapper over the key-value and relational traits that makes chosen operations fail on a schedule, for testing callers.
22. **Sized and concurrent timing (0.10.3 to 0.11.7).** Key-value workloads timed at any value size, several workloads compared with no combined score, a concurrent harness recording host load and free RAM per result. (Ideas 3 and the speed rows of the first pass already covered ranking by measured speed; this is the harness refinement and was not swept separately.)
